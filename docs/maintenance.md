## 一次变更如何完成

1. 确认是缺陷、维护事项还是新需求；业务范围关联已有RD-*，新增需求先更新PRD。
2. 按[技术路线](technical-route.md)和[架构](architecture.md)确定影响模块；兼容行为以目标客户端固定源码及已有用例为依据。
3. 修改代码与直接相关文档，保留现有数据、来源和历史证据；SQL变更同步两库迁移。
4. 按[开发指南](development.md)选择必要检查。文档改动只查链接与事实，业务改动跑受影响用例，协议变化才补对应实机流程；不默认全量重验。
5. 写明结果、实际执行范围和未覆盖项，更新[变更记录](../CHANGELOG.md)。交付或部署另记版本、镜像指纹与回退入口。

生产写入、凭据处理和账号收尾按实际授权执行，不能把一次文档整理扩大为自动上线、清理设备、重置密码或更新远端PR。

## 文档更新规则

| 变更 | 必须同步 |
|---|---|
| 功能范围、权限或用户流程 | PRD、业务逻辑、必要的验收条件 |
| 技术栈、模块或数据结构 | 技术路线/架构、开发指南和迁移说明 |
| CLI、配置或接口 | API/Web/deploy底层说明；上层文档引用，不复制整份参数表 |
| 生产部署或恢复 | 日期化部署记录、镜像指纹、运维入口和支持矩阵 |
| 上游客户端/hbbs兼容 | 来源提交、专项兼容记录、相关实机证据 |
| 已通过或略过的验证 | 当前验收汇总及独立结果文件；历史报告原范围不变 |

当前事实优先引用源码与最新适用记录；旧文档不正确的“当前状态”可以修正，但不能把后来的通过结果倒写成旧里程碑已经覆盖。历史讨论保留日期和替代入口，避免重新成为默认实施方案。

## 文件与交付边界

业务实现位于`api/`、`web/`，部署资产位于`deploy/`，可复现脚本与脱敏结果位于`validation/`。`upstream/`、`references/`是独立参考checkout，`fixes/`和`diagnostics/`是客户端专项资产。

`.runtime`、实际数据库、`.secrets`、凭据文件、key ring、原始日志和备份归私有运行资产；不复制进文档、镜像上下文或公开结果。现有`.gitignore`不能替代发布前文件审查，尤其是诊断输出和新增秘密目录。清理前先确认是否是PR构建的唯一副本或恢复所需密钥。

使用[支持矩阵](release-notes.md)说明实际边界，不以测试数量承诺容量、平台全集或SLA。生产操作按[运维手册](operations.md)执行；开发与文档维护不主动连接生产。
